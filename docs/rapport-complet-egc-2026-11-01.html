ÉGLISE GLORIEUSE DU CHRIST

Rapport complet de l'application EGC

État fonctionnel, statistiques, bugs, sécurité et capacité

Établi le 1er novembre 2026

Périmètre : frontend React/Vite, application Android/Capacitor, API Express, base SQLite, intégration YouTube, déploiement Railway et vérifications effectuées sur le domaine public.

Ce document décrit explicitement ce qui fonctionne, ce qui est volontairement désactivé, comment les données circulent, quels bugs ont été rencontrés, quelles corrections ont été déployées et quelles limites restent à traiter.

Les statistiques de code proviennent du dépôt analysé. Les chiffres de charge de production ne sont pas inventés : aucun test de 5 000 utilisateurs simultanés n'a été exécuté sur Railway.

1. Résumé exécutif

L'application EGC est une application web responsive et Android destinée à présenter l'église, ses événements, la Bible, les prédications YouTube, les invitations et l'administration des inscriptions et annonces.

État global : fonctionnel pour le périmètre actuellement activé, avec une réserve importante sur la montée en charge : le backend utilise encore SQLite synchrone et une seule instance est recommandée.
  • Frontend public Railway accessible : https://egliseglorieuseduchrist.up.railway.app.
  • API de production accessible : https://egc-front-production.up.railway.app.
  • Tests backend : 6 tests réussis sur 6, dont 2 000 inscriptions simulées.
  • Build frontend : Vite réussi.
  • Sécurité de base : Helmet, CORS allowlist, JWT, bcrypt, Zod, requêtes paramétrées et rate limiting.
  • Limite : PostgreSQL et Redis ne sont pas encore provisionnés ; le support garanti de 5 000 utilisateurs simultanés n'est donc pas démontré.

3. Architecture et circulation des données

  1. Le navigateur charge le bundle frontend depuis le service Railway frontend.
  2. frontend/src/services/apiConfig.js pointe la production vers le service API dédié.
  3. Les écrans publics lisent les annonces, vidéos et statut Live via des requêtes HTTPS.
  4. Les annonces et les prédications sont conservées en cache local pour afficher un contenu de secours.
  5. Les formulaires envoient du JSON au backend avec validation côté client et côté serveur.
  6. Les opérations d'administration nécessitent un JWT de 20 minutes dans l'en-tête Authorization.
  7. Le backend écrit les inscriptions, demandes de don et annonces dans SQLite.
  8. YouTube fournit le flux RSS des vidéos du dimanche et la page du direct.

6. Live et vidéos YouTube

  • Le backend vérifie la page Live de la chaîne EGC TV.
  • Lorsqu'un direct est détecté, l'API renvoie son identifiant et l'interface affiche le lecteur.
  • Lorsque le direct est inactif, l'écran indique « Aucun direct n'est en cours » et affiche les prédications.
  • Le flux RSS est filtré par le mot « dimanche » dans le titre.
  • Les quatre vidéos distinctes les plus récentes sont retournées et mises en cache cinq minutes côté API.
  • La vidéo du 1er novembre 2026 a été vérifiée comme valide avec l'identifiant YouTube UqNR2ZX3dXE.
  • Une erreur YouTube 153 a été rencontrée dans un lecteur intégré ; la politique de référent a été corrigée vers strict-origin-when-cross-origin.
Limite : la lecture dépend des règles YouTube, de l'autorisation d'intégration, de la disponibilité de la vidéo et de la connexion de l'utilisateur.

8. Sécurité actuelle

  • Helmet ajoute des en-têtes HTTP de protection.
  • CORS limite les origines autorisées à une allowlist.
  • Les secrets et mots de passe doivent venir des variables Railway ; le dépôt ne doit pas contenir de secrets.
  • Les mots de passe sont hachés avec bcrypt.
  • Les JWT sont vérifiés avec l'algorithme HS256 et expirent après 20 minutes.
  • Zod limite les types, tailles, formats et valeurs des entrées.
  • Les requêtes SQL utilisent des paramètres plutôt que de concaténer les entrées.
  • Les limites de requêtes publiques et de connexion réduisent les abus simples.
  • Les délais HTTP serveur sont bornés et les annonces publiques ont un cache court.
  • Les uploads d'administration sont réservés au JWT et limités en taille et type.
Risque restant : le rate limiting est local à l'instance. Avec plusieurs instances, il faut un store Redis partagé. SQLite synchrone doit être remplacé par PostgreSQL pour une montée en charge horizontale.

11. Limites et bugs encore ouverts

  1. Scalabilité : SQLite synchrone peut bloquer la boucle Node lors d'écritures concurrentes.
  2. Rate limiting distribué : les compteurs ne sont pas partagés entre plusieurs instances.
  3. Pagination : l'administration utilise encore OFFSET, moins efficace sur de très grandes pages.
  4. Chunks frontend : les données bibliques produisent de gros bundles ; le premier chargement peut être lent sur mobile.
  5. Paiement : /api/pay enregistre une intention ; il ne déclenche pas encore de paiement MTN réel ni de webhook signé.
  6. Live : si la page reste ouverte avant le début d'un direct, un rechargement est nécessaire pour obtenir le nouveau statut avec la logique actuelle.
  7. Observabilité : aucun tableau de bord p95/p99, tracing ou test de charge Railway automatisé n'est fourni dans le dépôt.

13. Conclusion

Le périmètre public actuellement activé est fonctionnel et les corrections demandées ont été déployées. Les cinq rubriques futures sont masquées puis accessibles au clic, sans suppression du code initial. Les liens sociaux et l'invitation pointent vers les adresses demandées. Le Live est relié à l'API et à YouTube.

La prochaine étape technique indispensable pour une promesse solide de plus de 5 000 utilisateurs est une migration PostgreSQL + Redis accompagnée d'un test de charge en environnement Railway. Jusqu'à cette étape, l'application doit être considérée comme robuste pour une instance et un trafic modéré, mais non comme une architecture multi-instance pleinement validée.
